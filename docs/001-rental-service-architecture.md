# ADR-001: использовать stateless Rental API с PostgreSQL и Redis

- **Статус:** Proposed - требуется ревью команды и преподавателя до реализации.
- **Дата:** 2026-11-09
- **Контекст:** домашнее задание 1, команда 9, "Аренда пауэрбанка".

## Контекст и проблема

Исходная заготовка реализует бизнес-логику функциями в `main.py` и хранит офферы
и заказы в словарях процесса. В ней есть три сценария:

1. Создание оффера: получение станции, тарифа, профиля пользователя и конфигурации;
   расчёт цены, бесплатного периода и депозита.
2. Начало аренды: создание заказа, резервирование депозита и выдача пауэрбанка
   со станции.
3. Возврат: фиксация возврата, расчёт суммы и завершение платежа.

Внешние зависимости заготовки: `stations`, `tariffs`, `users`, `configs` и
`payments`. Станции не только отдают данные, но и физически выдают пауэрбанк;
`payments` выполняет резервирование и списание средств.

Текущая реализация не подходит для задания: в ней нет постоянного хранилища,
собственного API основного сервиса, обработки ошибок интеграций, кэша,
масштабирования и наблюдаемости. Последовательность "резервирование -> выдача -> сохранение
заказа" также способна оставить данные и деньги в несогласованном состоянии.

## Границы ADR

Этот ADR фиксирует архитектуру, предлагаемую к утверждению для домашнего
задания: границы основного сервиса и внешних зависимостей, PostgreSQL как
источник истины, Redis для кэширования чтений, а также подходы к интеграциям,
надёжности и масштабированию.

Конкретные поля HTTP API, детали схемы таблиц, значения TTL и параметры retry
могут уточняться в ходе реализации, если это не изменяет принятое
архитектурное решение.

## Требования

### Функциональные

- Создавать актуальный оффер аренды по пользователю и станции.
- Начинать аренду: резервировать платёж, выдавать пауэрбанк и создавать заказ.
- Возвращать пауэрбанк, рассчитывать итоговую стоимость и завершать платёж.
- Предоставлять пользователю и сотруднику информацию об активной аренде и
  накопленной стоимости.
- Контролировать свежесть оффера.
- Поддерживать запуск в других странах: станция относится к стране, тариф
  содержит валюту.
- Удалять записи заказов старше одного года; срок хранения должен настраиваться
  по стране заказа.

### Нефункциональные

- Создание заказов: до **100 RPS** (`X = 100`).
- Просмотр сведений об аренде: в среднем **50** раз на одну аренду (`Y = 50`).
  При устойчивом потоке 100 новых аренд/с это даёт расчётную нагрузку до
  **5 000 RPS** на чтение аренды.
- Размер записи об аренде в БД: около **1 КБ** (`Z = 1 КБ`).
- Критичные источники: `stations`, `payments`.
- `configs`: кэш, обновляемый раз в минуту.
- `tariffs`: LRU-кэш; запись старше 10 минут невалидна; TTL настраивается
  конфигурацией.
- `users`: при недоступности использовать fallback "жадный прайсинг".
- Нужны maintainability, reliability, scalability, БД, нагрузочный эмулятор,
  отчёт с графиками и/или логами.

## Факторы выбора решения (Decision Drivers)

- До 100 RPS создания заказов и до 5 000 RPS чтения сведений об аренде.
- Сохранность заказов и платежных операций при перезапуске или масштабировании
  сервиса.
- Корректная работа с критичными `stations` и `payments`: нельзя считать
  аренду успешной, если банк не выдан или операция с деньгами не подтверждена.
- Управляемая деградация некритичных `users`, `tariffs` и `configs`.
- Хранение данных один год и возможность выполнять очистку без остановки
  сервиса.
- Простота локального воспроизводимого запуска и тестирования командой.
- Возможность развивать приложение без зависимости от in-memory состояния
  конкретного экземпляра API.

## Рассмотренные варианты

1. Оставить исходный однопроцессный сервис со словарями в памяти.
2. Построить stateless Rental API с PostgreSQL без распределённого кэша.
3. Построить stateless Rental API с PostgreSQL как источником истины и Redis
   для распределённого кэширования чтений.

## Итог решения (Decision Outcome)

**Выбран вариант 3: stateless Rental API с PostgreSQL и Redis, при этом
внешние источники разворачиваются отдельно от основной логики.**

Он выбран, поскольку одновременно выполняет ключевые drivers: PostgreSQL
сохраняет заказы и операции платежей, stateless API можно горизонтально
масштабировать, а Redis снижает нагрузку на БД при преобладающих чтениях до
5 000 RPS. Вариант 1 не обеспечивает надёжность и масштабирование; вариант 2
сохраняет надёжность, но не даёт выделенного механизма для дешёвого
масштабирования частого чтения.

## Решение

### Границы сервисов

Решение состоит минимум из следующих независимо развёртываемых компонентов:

```text
Клиент / нагрузочный генератор
              |
        [Rental API]  <---->  [Redis]
              |
         [PostgreSQL]
              |
      интеграционные адаптеры
  _________|_____|___________
  |       |       |          |
stations payments users  tariffs/configs
  (отдельные сервисы-эмуляторы)
```

1. **Rental API** - stateless-сервис с публичным HTTP API. Он реализует
   офферы, аренды, возвраты, просмотры и оркестрацию интеграций. Несколько его
   экземпляров могут работать за балансировщиком.
2. **PostgreSQL** - единственный источник истины для офферов, аренд и операций
   платежей. Данные не должны храниться только в памяти процесса.
3. **Redis** - распределённый кэш для высокочастотного чтения активной аренды,
   а также для кэшей тарифов и конфигурации. Redis не является источником
   истины.
4. **Внешние сервисы-эмуляторы** - отдельно разворачиваемые `stations`,
   `payments`, `users`, `tariffs`, `configs`. На первом этапе допускается
   объединить их в один процесс-заглушку, но они не входят в Rental API и имеют
   отдельные HTTP-контракты.
5. **Фоновый worker** - выполняет очистку данных с истёкшим сроком хранения.
   На старте может жить в том же deployable-образе, но запускается отдельным
   процессом/командой и не обслуживает HTTP-запросы.

### Хранение данных

В PostgreSQL вводятся сущности:

- `offers`: идентификатор, пользователь, станция, зафиксированные тарифные
  условия, валюта, время создания и время истечения;
- `rentals`: идентификатор, пользователь, пауэрбанк, начальная и конечная
  станции, страна, валюта, цена, бесплатный период, депозит, статусы, времена
  начала/окончания и итоговая сумма;
- `payment_operations`: идентификатор операции, `rental_id`, тип
  (`reserve`, `capture`, `release`), сумма, idempotency key, статус и данные
  внешнего ответа;
- при необходимости - таблицы аудита или заданий очистки.

Для чтения аренды используются индексы по `rental_id`, `user_id`,
`powerbank_id`, статусу и времени окончания. Таблицу аренд надо
партиционировать по времени завершения/создания, если нагрузочный расчёт или
объём данных это подтвердят. Очистка удаляет или отбрасывает партиции старше
настроенного срока хранения.

### API и бизнес-правила

Минимальный публичный контракт Rental API:

- `POST /offers` - создать оффер;
- `POST /rentals` - начать аренду по офферу;
- `GET /rentals/{rental_id}` - получить активную или завершённую аренду;
- `POST /rentals/{rental_id}/return` либо `POST /returns` - зарегистрировать
  возврат пауэрбанка.

Оффер хранит тарифные условия как снимок на момент расчёта и имеет ограниченный
срок жизни. При начале аренды оффер может быть использован только один раз.

### Кэширование

- **Аренда:** `GET /rentals/{id}` читает Redis. При cache miss данные берутся
  из PostgreSQL и помещаются в кэш. При старте, возврате или изменении суммы
  запись кэша обновляется или инвалидируется после успешной транзакции БД.
- **Tariffs:** LRU-кэш с TTL из конфигурации, но не более 10 минут. Просроченная
  запись не используется как актуальная.
- **Configs:** кэш со штатным обновлением раз в минуту. Последнее корректно
  полученное значение может использоваться при кратком сбое источника, что
  должно логироваться и быть ограничено явно заданным TTL.
- **Users:** данные профиля не являются обязательными для расчёта при сбое:
  применяется "жадный прайсинг" - не выдаются скидки подписки и доверенного
  пользователя, берётся обычная цена и стандартный депозит.

### Надёжность и согласованность

- Для всех HTTP-вызовов задаются connect/read timeout, ограниченное число
  повторов только для безопасных операций и структурированные логи ошибок.
- Операции с `payments` передаются с idempotency key, равным стабильному ключу
  операции заказа. Повтор запроса не должен повторно списывать или резервировать
  деньги.
- `stations` и `payments` критичны: при недоступности пользователь получает
  явную ошибку, а операция не объявляется успешной.
- Начало аренды реализуется как saga с компенсацией, а не как распределённая
  транзакция: при неуспехе выдачи после резервирования выполняется отмена
  резервирования; при
  сбое после выдачи создаётся/доставляется задача для согласования заказа и
  станции. Состояния этапов сохраняются в БД.
- Оффер атомарно переводится из доступного в использованный в транзакции БД,
  чтобы исключить двойной старт аренды.

### Масштабирование и эксплуатация

- Rental API не хранит пользовательского состояния в локальной памяти и
  масштабируется горизонтально.
- Основная нагрузка - чтение до 5 000 RPS; Redis уменьшает количество чтений
  из PostgreSQL. База данных остаётся надёжным источником истины.
- Добавляются `/health` и `/ready`, метрики RPS, latency p50/p95/p99,
  cache-hit ratio, ошибки интеграций и число компенсаций платежей.
- Развёртывание описывается Docker Compose; production-подобный вариант
  предусматривает балансировщик перед несколькими экземплярами Rental API.

## Последствия

### Положительные

- Постоянная БД устраняет потерю заказов при перезапуске.
- Redis и stateless API позволяют обслуживать преобладающую нагрузку чтения.
- Явные состояния платежей, идемпотентность и компенсации уменьшают риск
  потери денег или двойного списания.
- Изоляция внешних систем упрощает тестирование отказов и независимое
  развертывание.

### Отрицательные и риски

- Появляются Redis, миграции БД, инвалидация кэша, фоновая очистка и
  мониторинг - система сложнее исходной заготовки.
- Saga допускает кратковременную eventual consistency между заказом, платёжной
  системой и станцией; нужны ретраи и аудит незавершённых операций.
- Расчёт 5 000 RPS основан на устойчивом потоке 100 новых аренд/с и среднем
  `Y = 50`; реальный нагрузочный профиль надо подтвердить эмулятором.

## Отклонённые альтернативы

1. **Оставить словари в памяти.** Отклонено: данные теряются при перезапуске,
   нельзя безопасно запускать несколько экземпляров сервиса.
2. **Один монолитный процесс с заглушками и без БД.** Отклонено: не выполняет
   требования о БД, отдельных сервисах, надёжности и масштабировании.
3. **Только PostgreSQL без кэша.** Отклонено: сервису предстоит интенсивное
   чтение данных аренды; кэш уменьшает давление на БД и задержки чтения.
4. **Считать недоступность `stations` или `payments` успехом.** Отклонено:
   эти источники критичны, а такое поведение приводит к потере контроля над
   деньгами или физическим пауэрбанком.

## Проверка решения

Решение принимается, если:

- интеграционные и unit-тесты покрывают счастливые пути и сбои каждого
  источника;
- нагрузочный сценарий воспроизводит 100 RPS создания и соотношение до 50
  просмотров на одну аренду;
- в отчёте есть latency, error rate, cache-hit ratio и логи/графики;
- демонстрируется восстановление после недоступности `stations`, `payments`
  и fallback для `users`;
- Docker Compose поднимает сервисы, БД, Redis и эмуляторы воспроизводимо.
