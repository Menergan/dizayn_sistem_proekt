# ADR-001: использовать stateless Rental API с PostgreSQL и Redis

- **Статус:** Proposed - требуется ревью команды и преподавателя до реализации.
- **Дата:** 2026-11-09
- **Контекст:** домашнее задание 1, команда 9, "Аренда пауэрбанка".

## Контекст и проблема

Исходная заготовка реализует бизнес-логику функциями в `main.py` и хранит офферы
и заказы в словарях процесса. В ней есть три сценария:

1. Создание оффера: получение станции, тарифа, профиля пользователя и конфигурации;
   расчёт цены, бесплатного периода и депозита.
2. Начало аренды: создание заказа, резервирование депозита и выдача пауэрбанка
   со станции.
3. Возврат: фиксация возврата, расчёт суммы и завершение платежа.

Внешние зависимости заготовки: `stations`, `tariffs`, `users`, `configs` и
`payments`. Станции не только отдают данные, но и физически выдают пауэрбанк;
`payments` выполняет резервирование и списание средств.

Текущая реализация не подходит для задания:
- Офферы и заказы хранятся в словарях в памяти процесса. При перезапуске
  приложения эти данные теряются. (надёжность)
- Состояние хранится локально в одном процессе. При запуске нескольких
  экземпляров приложения у каждого будет собственный набор данных, поэтому
  запросы к разным экземплярам могут возвращать разные результаты. (масштабируемость)
- При начале аренды выполняются две операции: резервирование
  платежа и выдача пауэрбанка. Если одна завершится ошибкой,
  а другая уже успеет выполниться, потребуется отдельная логика отмены
  или восстановления операции. (согласованность операций)


## Требования

### Функциональные

- Создавать актуальный оффер аренды по пользователю и станции.
- Начинать аренду: резервировать платёж, выдавать пауэрбанк и создавать заказ.
- Возвращать пауэрбанк, рассчитывать итоговую стоимость и завершать платёж.
- Предоставлять пользователю и сотруднику информацию об активной аренде и
  накопленной стоимости.
- Контролировать свежесть оффера.
- Поддерживать запуск в других странах: станция относится к стране, тариф
  содержит валюту.
- Удалять записи заказов старше одного года; срок хранения должен настраиваться
  по стране заказа.

### Нефункциональные

- Создание заказов: до **100 RPS** (`X = 100`).
- Просмотр сведений об аренде: в среднем **50** раз на одну аренду (`Y = 50`).
  При устойчивом потоке 100 новых аренд/с это даёт расчётную нагрузку до
  **5 000 RPS** на чтение аренды.
- Размер записи об аренде в БД: около **1 КБ** (`Z = 1 КБ`).
- Критичные источники: `stations`, `payments`.
- `configs`: кэш, обновляемый раз в минуту.
- `tariffs`: LRU-кэш; запись старше 10 минут невалидна; TTL настраивается
  конфигурацией.
- `users`: при недоступности использовать fallback "жадный прайсинг".
- Нужны maintainability, reliability, scalability, БД, нагрузочный эмулятор,
  отчёт с графиками и/или логами.

## Факторы выбора решения (Decision Drivers)

- До 100 RPS создания заказов и до 5 000 RPS чтения сведений об аренде.
- Сохранность заказов и платежных операций при перезапуске или масштабировании
  сервиса.
- Корректная работа с критичными `stations` и `payments`: нельзя считать
  аренду успешной, если банк не выдан или операция с деньгами не подтверждена.
- Обслуживание до 5 000 RPS запросов на чтение аренды без выполнения
  каждого запроса непосредственно к PostgreSQL.

## Рассмотренные варианты

1. Построить stateless Rental API с PostgreSQL без распределённого кэша.
2. Построить stateless Rental API с PostgreSQL как источником истины и Redis
   для распределённого кэширования чтений.

## Итог решения (Decision Outcome)

**Выбран вариант 2: stateless Rental API с PostgreSQL и Redis, при этом
внешние источники разворачиваются отдельно от основной логики.**

## Решение

### Границы сервисов

Решение состоит минимум из следующих независимо развёртываемых компонентов:

```text
                 Клиент
                    |
             [Балансировщик]
                    |
              [Rental API]
               /        \
          [Redis]    [PostgreSQL]
                    |
          HTTP-вызовы из Rental API
                    |
       +------------+-------------+
       |            |             |
   [stations]  [payments]      [users]
                                |
                         [tariffs/configs]

       [Фоновый worker] ---> [PostgreSQL]
```

1. **Rental API** - stateless-сервис с публичным HTTP API. Он реализует
   офферы, аренды, возвраты, просмотры и оркестрацию интеграций. Несколько его
   экземпляров могут работать за балансировщиком.
2. **PostgreSQL** - единственный источник истины для офферов, аренд и операций
   платежей. Данные не должны храниться только в памяти процесса.
3. **Redis** - распределённый кэш для высокочастотного чтения активной аренды.
   Redis не является источником истины.
4. **Внешние сервисы-эмуляторы** - отдельно разворачиваемые `stations`,
   `payments`, `users`, `tariffs`, `configs`. На первом этапе допускается
   объединить их в один процесс-заглушку, но они не входят в Rental API и имеют
   отдельные HTTP-контракты.
5. **Фоновый worker** - выполняет очистку данных с истёкшим сроком хранения.
   На старте может жить в том же deployable-образе, но запускается отдельным
   процессом/командой и не обслуживает HTTP-запросы.

### Хранение данных

В PostgreSQL вводятся сущности:

- `offers`: идентификатор, пользователь, станция, зафиксированные тарифные
  условия, валюта, время создания, время истечения и статус (`AVAILABLE`, `USED`, `EXPIRED`).
- `rentals`: идентификатор, пользователь, пауэрбанк, начальная и конечная
  станции, страна, валюта, цена, бесплатный период, депозит, статус (`CREATING`, `ACTIVE`, `RETURNING`, `COMPLETED`, `FAILED`), времена
  начала/окончания, итоговая сумма и `delete_after`;
- `payment_operations`: идентификатор операции, `rental_id`, тип
  (`reserve`, `capture`, `release`), сумма, idempotency key, статус и данные
  внешнего ответа;

Для чтения аренд создаются индексы по `user_id`, `powerbank_id` и статусу
аренды. `rental_id` является первичным ключом.

При завершении аренды Rental API определяет срок хранения по стране заказа
(по умолчанию один год) и сохраняет вычисленное время удаления в `delete_after`.
Worker раз в час удаляет завершённые аренды с истёкшим `delete_after`
пакетами по индексированному полю. Таблица `rentals` на текущем этапе не
партиционируется: PostgreSQL требует включать ключ партиционирования в каждый
первичный и уникальный ключ. Партиционирование по `delete_after` потребовало бы
составного ключа с `rental_id`, что несовместимо с глобальным идентификатором
аренды, внешними ключами `payment_operations` и `station_events`.

Пакетное удаление ограничивает длительность транзакции и блокировок. Решение о
выделении отдельного архива завершённых аренд с партиционированием принимается
после нагрузочного тестирования и отдельного согласования модели внешних ключей.

### API и бизнес-правила

Минимальный публичный контракт Rental API:

- `POST /offers` - создать оффер;
- `POST /rentals` - начать аренду по офферу;
- `GET /rentals/{rental_id}` - вернуть идентификатор аренды, пользователя и пауэрбанка, статус, время начала и возврата, страну, валюту, продолжительность аренды, депозит и накопленную стоимость. Для завершённой аренды дополнительно возвращается итоговая стоимость; для активной накопленная стоимость рассчитывается на момент запроса.
- `POST /station-events/powerbank-returned` - внутренний callback от `stations`
  о физическом возврате пауэрбанка.

Оффер хранит тарифные условия как снимок на момент расчёта и имеет ограниченный
срок жизни. При начале аренды оффер может быть использован только один раз. Денежные значения обрабатываются с использованием `Decimal`, а округление выполняется до минимальной денежной единицы соответствующей валюты по правилу `ROUND_HALF_UP`.


#### Срок действия оффера

- При создании оффера фиксируются условия тарифа, валюта, размер депозита и время истечения срока действия `expires_at`.
- Срок действия оффера составляет 5 минут с момента создания. Этого достаточно, чтобы пользователь подтвердил аренду, но период уменьшает риск выдачи пауэрбанка по устаревшим цене, тарифу или данным о доступности.
- При начале аренды проверяется, что оффер существует, не истёк и ещё не использовался.
- Один оффер может быть использован только для одной аренды.
- Если срок действия оффера истёк, создание аренды по нему отклоняется. Пользователь должен запросить новый оффер.
- Изменение тарифов после создания оффера не меняет сохранённые в нём условия. До истечения срока действия пользователь может начать аренду по ранее полученному офферу.
- Worker удаляет истёкшие неиспользованные офферы пакетами по `expires_at`.

### Кэширование

**Аренды:**
- `GET /rentals/{id}` сначала проверяет наличие данных аренды в Redis.
- При отсутствии записи данные загружаются из PostgreSQL и помещаются
  в Redis с TTL 5 минут. TTL ограничивает срок жизни неактуальной записи и
  освобождает память, если инвалидация не произошла.
- В Redis хранятся все данные, нужные для ответа и расчёта: `start_time`, `price_per_hour`, `free_period_min`, валюта, депозит, статус, идентификаторы аренды, пользователя, пауэрбанка и станции.
- Для активной аренды накопленная стоимость рассчитывается на каждом запросе
  из текущего времени, `start_time` и сохранённых тарифных условий. При cache hit обращение к PostgreSQL не требуется. При cache miss данные берутся из PostgreSQL, после чего создаётся запись Redis.
- После начала аренды, возврата или изменения данных аренды запись
  в Redis удаляется. При следующем чтении она загружается из PostgreSQL.
- Redis автоматически удаляет записи по истечении TTL. Отдельный worker для очистки кэша не нужен.

**Тарифы:**
- Для тарифов используется локальный LRU-кэш внутри каждого экземпляра Rental API.
- Кэш уменьшает число синхронных HTTP-вызовов в `tariffs` при создании офферов. `tariff_id` - ключ кеша.
- При отсутствии записи или истечении TTL данные запрашиваются у сервиса
  `tariffs` и сохраняются в локальном кэше.
- TTL задаётся конфигурацией в диапазоне от 1 до 600 секунд. Верхняя граница 600 секунд следует из требования, что данные тарифа старше 10 минут невалидны.
- Если сервис `tariffs` недоступен, а в кэше нет актуального значения,
  операция, требующая тариф, завершается ошибкой. Устаревшие данные
  не используются.
- У разных экземпляров Rental API кэш независимый. Поэтому после изменения
  тарифа возможна кратковременная разница между экземплярами, но данные
  старше установленного TTL не используются.

**Конфигурация:**
- Каждый экземпляр Rental API хранит собственную локальную копию конфигурации.
- При запуске экземпляр получает конфигурацию от сервиса `configs`.
  До успешной первой загрузки он не переходит в состояние готовности
  принимать запросы.
- После первой загрузки конфигурация обновляется запросом к сервису
  `configs` раз в минуту.
- При ошибке обновления используется последняя успешно полученная версия
  конфигурации. Ошибка обновления записывается в лог.
- Поскольку кэш локальный, разные экземпляры могут получить новую
  конфигурацию с небольшой задержкой.

**Users:**
- При недоступности `users` Rental API не получает сведения о подписке и доверенности пользователя.
- Применяется fallback "жадный прайсинг": скидка по подписке не применяется,
  используется базовая цена тарифа, а депозит устанавливается таким же, как и `default_deposit`.
- Fallback применяется только при технической недоступности `users`.
- Использование fallback фиксируется в логах.

### Надёжность и согласованность

- Timeout не является бизнес-настройкой и не изменяется через `configs`.
  Connect и read timeout задаются при развёртывании отдельно для каждого
  внешнего сервиса и уточняются по результатам нагрузочного тестирования.
  Это защищает пул соединений Rental API от зависших запросов.
- Повторяются только операции, повторный вызов которых не приводит к повторному
  изменению состояния. Ошибки интеграций записываются в структурированные логи.
- Idempotency key нужен только для команд, изменяющих финансовое состояние:

  | Операция | Idempotency key |
  | --- | --- |
  | Резервирование депозита | `rental:{rental_id}:reserve` |
  | Списание итоговой суммы | `rental:{rental_id}:capture` |
  | Отмена резервирования | `rental:{rental_id}:release` |

  Ключ детерминированно строится из UUID аренды и типа операции. Он сохраняется
  в `payment_operations` до первого вызова `payments`; уникальное ограничение
  `(rental_id, operation_type)` не позволяет создать второй ключ. При повторе
  используется сохранённый ключ. GET-запросам к `users`, `tariffs` и `configs`
  idempotency key не нужен.
- Выдача пауэрбанка тоже изменяет внешнее состояние. Для неё Rental API создаёт
  и сохраняет `station_operation_id` со значением `rental:{rental_id}:eject`.
  При timeout повторный запрос к `stations` использует тот же идентификатор,
  чтобы не выдать второй пауэрбанк.
- `stations` и `payments` являются критичными зависимостями. Если один
  из этих сервисов недоступен, начало аренды не подтверждается пользователю.
- Начало аренды выполняется с сохранением промежуточного состояния в PostgreSQL:
  1. Rental API создаёт запись аренды со статусом `CREATING` и запись
     операции резервирования платежа.
  2. Выполняет резервирование депозита через `payments` с idempotency key.
  3. При успешном резервировании сохраняет его результат и вызывает
     `stations` для выдачи пауэрбанка.
  4. При успешной выдаче сохраняет идентификатор пауэрбанка и переводит
     аренду в статус `ACTIVE`.
  5. Если выдача не удалась, Rental API вызывает `payments` для отмены
     резервирования и переводит аренду в статус `FAILED`.
- Если результат вызова внешнего сервиса неизвестен из-за тайм-аута,
  Rental API проверяет состояние операции по её идентификатору или повторяет
  запрос с тем же idempotency key, если внешний сервис поддерживает такую
  операцию. Компенсация выполняется только после подтверждения результата.
- Незавершённые аренды со статусом `CREATING` обрабатываются фоновым worker:
  он проверяет состояние внешних операций и завершает аренду либо выполняет
  компенсацию. Промежуточное состояние хранится в PostgreSQL, поэтому
  обработку можно продолжить после перезапуска Rental API.
- Оффер атомарно переводится из доступного в использованный в транзакции БД,
  чтобы исключить двойной старт аренды.
- Возврат инициирует `stations` после физического приёма пауэрбанка. Сервис
  вызывает защищённый callback `POST /station-events/powerbank-returned` и
  передаёт `station_id`, `powerbank_id`, `returned_at` и `station_event_id`.
  Rental API сохраняет `station_event_id` с уникальным ограничением, поэтому
  повторный callback не создаёт повторное списание. Активная аренда находится
  по `powerbank_id` и статусу `ACTIVE`.
- Возврат аренды выполняется с сохранением состояния операции в PostgreSQL:
  1. Rental API принимает событие от `stations`, регистрирует начало возврата
     и атомарно переводит найденную аренду в статус `RETURNING`.
  2. Рассчитывает итоговую стоимость по условиям тарифа, сохранённым
     в аренде.
  3. Вызывает `payments` для завершения платежа с idempotency key.
  4. После подтверждения платежа переводит аренду в статус `COMPLETED`
     и сохраняет итоговую стоимость.
- Если завершение платежа не удалось, аренда остаётся в промежуточном
  состоянии. Фоновый worker повторно обрабатывает операцию с тем же
  idempotency key, пока не получит окончательный результат.

### Технологический стек

- **Язык:** Python 3.13.
- **HTTP API:** FastAPI.
- **Работа с PostgreSQL:** SQLAlchemy 2 и Alembic для миграций.
- **Работа с Redis:** redis-py.
- **HTTP-клиент для внешних сервисов:** httpx.
- **Тестирование:** pytest.
- **Нагрузочное тестирование:** Locust.
- **Развёртывание:** Docker и Docker Compose.

Выбор Python и FastAPI обусловлен тем, что исходная бизнес-логика уже реализована на Python и использует FastAPI. Это позволяет сохранить существующую реализацию и не тратить время на перенос логики на другой стек.

### Масштабирование и эксплуатация

- Rental API не хранит пользовательского состояния в локальной памяти и
  масштабируется горизонтально.
- Основная нагрузка - до 5 000 RPS на чтение. Redis уменьшает количество
  обращений к PostgreSQL, которая остаётся источником истины.
- Добавляются `/health` и `/ready`, метрики RPS, latency p50/p95/p99,
  cache-hit ratio, ошибки и latency Redis, ошибки интеграций и количество
  компенсационных операций.
- Для локального развёртывания используется Docker Compose. Nginx принимает
  внешний HTTP-трафик и распределяет его между семью stateless-репликами
  Rental API. Access-log Uvicorn и Nginx отключён для нагрузочного профиля.
- Redis и PostgreSQL используют ограниченные пулы соединений и таймауты.
  При ошибке Redis чтение ограниченно переходит к PostgreSQL. Если лимит
  fallback исчерпан, API отвечает `503`, не создавая неограниченную очередь
  запросов к PostgreSQL.

**Расчёт API-реплик:**

Расчётная производительность одной реплики принимается равной 800 RPS при
загрузке CPU не выше 70%. Для нагрузки 5 000 RPS требуется:

```text
ceil(5 000 / 800) = 7 реплик
```

Семь реплик обеспечивают расчётную суммарную производительность 5 600 RPS.
Это даёт запас 600 RPS относительно целевой нагрузки. Значение 800 RPS -
подтверждённая стрельбой ёмкость одной реплики при ограничении CPU 70%.

**Расчёт объёма данных для production:**

```text
100 аренд/с x 86 400 с/сутки = 8,64 млн аренд/сутки
8,64 млн аренд/сутки x 365 суток = 3,154 млрд аренд/год
3,154 млрд аренд x 1 КБ = около 3,15 ТБ данных без индексов
```

С учётом индексов, служебных данных PostgreSQL и запаса требуется около 6-8 ТБ
на primary PostgreSQL. Реплика требует такой же объём, поэтому для хранения
годового объёма данных нужно предусмотреть не менее 12-16 ТБ суммарного
дискового пространства. Внешние `stations`, `payments` и другие источники масштабируются независимо.

При TTL 5 минут верхняя граница числа уникальных записей в Redis составляет
`5 000 RPS x 300 с = 1,5 млн` записей. При размере снимка до 1 КБ, двукратном
запасе на служебные данные Redis и дополнительном двукратном запасе получается
около 6 ГБ. Поэтому 8 ГБ RAM на Redis primary и 8 ГБ на replica достаточны для этой верхней оценки. Реальный расход и cache-hit ratio измеряются нагрузочным тестом.

**Предварительная production-конфигурация:**

| Компонент | Количество и ресурсы |
| --- | --- |
| Балансировщик | 2 экземпляра по 2 vCPU и 4 ГБ RAM |
| Rental API | 7 экземпляров по 4 vCPU и 8 ГБ RAM |
| Redis | primary и replica, по 4 vCPU и 8 ГБ RAM |
| PostgreSQL | primary и standby, по 8 vCPU, 64 ГБ RAM и 8 ТБ NVMe |
| Worker | 2 экземпляра по 2 vCPU и 4 ГБ RAM |

Конфигурация является production-оценкой. Её достаточность подтверждается
стрельбой на 800 RPS на реплику при загрузке CPU не выше 70%. В эксплуатации
контролируются p95/p99, IOPS, cache-hit ratio, ошибки Redis и задержки
PostgreSQL.
