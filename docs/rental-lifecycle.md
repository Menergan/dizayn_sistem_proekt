# Участник 4: жизненный цикл аренды

Реализация следует `docs/001-rental-service-architecture.md` из ветки `adr`.
С разрешения пользователя эмулятор участника 2 дополнен передачей
Bearer-токена из STATION_CALLBACK_TOKEN. Другие исходники участников 1–3
не изменены. Новая точка входа
`app.lifecycle.api:app` подключает их приложение, включая чтение и метрики,
и добавляет POST /rentals и защищённый callback станции. Старый запуск
`app.main:app` сам по себе новых маршрутов не содержит.

## Запуск

Python 3.13, зависимости из Pipfile. Для миграций задать
DATABASE_MIGRATIONS_URL с драйвером postgresql+psycopg и применить
`alembic upgrade head`.
Задать DATABASE_URL, REDIS_URL, EXTERNAL_SERVICES_URL и STATION_CALLBACK_TOKEN.

```sh
uvicorn app.lifecycle.api:app --host 0.0.0.0 --port 8000
python -m app.lifecycle.worker
pytest tests/rental_lifecycle
```

Или задать STATION_CALLBACK_TOKEN и выполнить:

```sh
docker compose -f docker-compose.yml -f docker-compose.lifecycle.yml up --build
```

POST /rentals принимает `{"offer_id": "UUID"}` существующего оффера.
Повтор того же offer_id возвращает ту же аренду; просроченный или уже занятый
другим механизмом оффер даёт 409. Создание офферов относится к участнику 3.
Callback принимает station_id, powerbank_id, returned_at (с часовым поясом),
station_event_id (UUID) и требует `Authorization: Bearer <STATION_CALLBACK_TOKEN>`.
Проверять callback можно прямым HTTP-запросом с этим заголовком.

## Согласованность

Новая миграция добавляет журнал rental_lifecycle с уникальным offer_id,
этапом саги и station_operation_id. Использование оффера, создание аренды
и журнала проходят одной транзакцией. Резервирование регистрируется в
payment_operations до внешнего запроса. Каждый последующий результат
сохраняется до перехода к следующему внешнему действию.

Транзакционные advisory locks PostgreSQL сериализуют обработку аренды между
API и worker; отдельный пул без переиспользования соединений для блокировок
не занимает пул бизнес-транзакций. При падении процесса соединение закрывается
и блокировка освобождается. Возврат и запись уникального события атомарны.
Дубликат события с другим содержимым отклоняется.

Timeout или ошибка транспорта не означает подтверждённый отказ. Worker
повторяет операцию с прежним ключом. Только явный successful=false от станции
запускает release. До подтверждения release аренда остаётся CREATING.
После неуспешного capture аренда остаётся RETURNING. Если внешняя система
навсегда сохраняет отрицательный результат по ключу, требуется разбор причины
оператором; новый финансовый ключ автоматически не создаётся.

Расчёт итоговой стоимости использует существующее правило участника 3:
полные часы с ROUND_HALF_UP, бесплатный период и снимок тарифа. Это сохраняет
совпадение стоимости чтения и списания. Срок хранения берётся из configs по
стране. Инвалидация Redis выполняется после изменения состояния, ошибки
пишутся в лог; существующий TTL ограничивает время устаревшего кэша.

## Проверки

Unit-тесты используют fake-хранилище, клиентов и кэш: успешный цикл,
конкурентные повторы старта, отказ резервирования, компенсация отказа станции,
потеря ответа после внешнего эффекта на каждом этапе, перезапуск обработчика,
дубли callback, ошибка списания и некорректное время возврата.

Проверки PostgreSQL запускаются с LIFECYCLE_TEST_DATABASE_URL на отдельной
тестовой БД после миграций. Они проверяют конкурентный старт и возврат,
отклонение просроченного оффера и изменение содержимого повторного события.
